## Story

**As an** OxideZap user,
**I want** the attachment button to offer Document and Photos & videos categories,
**so that** I can choose the intended WhatsApp attachment type before selecting a file.

## Context and Decisions

The attachment button currently provides the existing file-selection flow, and Story 1.6 added an explicit confirmation before accepted attachments are sent. The user requests the two file categories shown in WhatsApp Web: **Documento** and **Fotos e vídeos**. The latter is one combined category; the selected file's MIME/type continues to distinguish an image from a video for the existing attachment path. **Documento** is an explicit user choice to send the original file as a document, even when its content is JPG, MP4, HEIC, or another media type.

Each category must guide selection and preserve the corresponding attachment kind through the existing preview and send path. The category menu is only a selection aid; it must not bypass the confirmation surface or introduce a second upload pipeline. On browser paths, use the native file input's `accept` hint for **Fotos e vídeos** when available; **Documento** must remain broad because any valid file may be sent as a document. On macOS, `gpui::PathPromptOptions` does not provide an extension filter, so the native picker may show all files; the selected result must still be validated after selection and the **Fotos e vídeos** category must reject incompatible files clearly.

This story concerns the attachment button. Existing clipboard-image, drag/drop, and their confirmation behavior remain intact unless they share the common selection/confirmation code and require a regression guard. No caption editor, media editor, new attachment transport, or unrelated file-management behavior is added.

The other WhatsApp Web attachment entries visible in the reference — camera, audio, contact, poll, event, and sticker — are separate resources and are outside this story.

## Acceptance Criteria

1. Activating the attachment button opens a category surface with the two user-facing choices **Documento** and **Fotos e vídeos**. Dismissing the category surface makes no selection and sends nothing.
2. Choosing **Fotos e vídeos** uses the browser file input's `accept` hint for supported image/video types where that capability exists. On macOS, where the native `PathPromptOptions` picker cannot filter extensions visually, every selected result is validated after selection; a non-image/non-video result is refused clearly and is never sent as a document.
3. A valid image selected through **Fotos e vídeos** preserves the image MIME/type and existing image attachment kind; a valid video selected through the same category preserves the video MIME/type and existing video attachment kind. The combined category does not collapse either type into a generic file.
4. Choosing **Documento** accepts any valid selected file, including JPG, MP4, HEIC, and other image/video files, subject to the existing empty-file, size, and refusal rules. It preserves the original filename, MIME/type metadata, and bytes while explicitly mapping the outgoing payload to `OutgoingMedia::Document`; a media file chosen under this category is not sent through the image/video preview kind.
5. Selecting a category or choosing files never sends immediately. Accepted files enter the existing explicit attachment confirmation surface before any upload, `send_attachment` call, or outgoing bubble.
6. The confirmation identifies the accepted files and their resolved category/type, retains the destination and existing reply-on-first-file behavior, and keeps the established `Cancel`/`Send` semantics: cancel sends zero files; confirm consumes the pending selection once and sends each accepted file exactly once.
7. Unsupported, refused, empty, or canceled selections follow the existing validation and notice behavior. A selection that yields no accepted files opens no confirmation and sends nothing.
8. The category chosen from the button is authoritative: **Documento** intentionally sends any valid file as `OutgoingMedia::Document`, while **Fotos e vídeos** accepts only compatible image/video media and refuses an incompatible result instead of silently falling back to a document. Existing clipboard-image and drag/drop confirmation flows continue to work and are covered by regression tests.
9. Automated tests cover category rendering/activation, browser `accept` hints where available, post-selection validation on macOS and browser paths, image/video MIME/type mapping, document mapping for ordinary files and JPG/MP4/HEIC-like media while preserving name/MIME/bytes, dismissal and empty selections, no send before confirmation, cancel-zero, confirm-exactly-once, refusal handling, destination/reply capture, and regressions for clipboard and drag/drop paths.
10. Repository Cargo formatting, clippy, and workspace tests pass; manual desktop smoke verifies both button categories, including an image and a video under **Fotos e vídeos**, and confirms that each accepted selection reaches the preview before sending.

## Test Seams

- Attachment button -> category choice -> browser `accept` hint or native picker -> post-selection validation -> existing `Chosen`/`Picked` representation; assert category-to-kind mapping and no send during selection.
- Accepted categorized files -> shared pending confirmation -> Cancel or Send; assert zero sends on cancel and exactly one send per accepted file on confirm, with captured chat/reply.
- Unsupported/refused/empty picker result -> existing notice/no-preview behavior; assert clipboard-image and drag/drop still use confirmation.
